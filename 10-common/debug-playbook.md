# 定位法：从现象到证据

先分类，再按类走对应第一步。**没有分类就开始读代码，是最贵的错误。**

## 0. 三步通用起手

1. **确定软硬件边界**：写一个已知寄存器再回读。读回不一致 → 总线/时钟/电源/复位层面，不要去查驱动逻辑。
2. **确定 OS 边界**：这条命令到硬件了吗？确认 doorbell 是否真被写（另一颗核、仿真器或寄存器 trace）。
3. **确定时间点**：记录第一次异常的时刻，与最近一次配置变更（时钟、电源、复位、固件版本）对齐。

## 1. 现象分类与第一步

| 现象 | 第一步 | 常见根因方向 |
|---|---|---|
| 整机挂死 / 无响应 | 回读任意寄存器确认总线是否活着 | 时钟被门控、电源域掉电、总线 hang、固件死循环 |
| 命令超时 | 查 doorbell 是否落下 + 环的 owner 位 | 提交未触发、中断被屏蔽、固件未处理、fence 无人 signal |
| 数据错误 / 结果不对 | 单算子小输入复现 + 抓 DMA 落地数据 | cache 未 invalidate、描述符长度或对齐错、地址翻译错 |
| 性能不达标 | 先分清算力受限还是带宽受限 | 利用率口径错、tile 切分不合理、频繁进出低功耗 |
| 内存 / 资源泄漏 | 数三类计数：buffer、映射、中断 | 错误路径漏释放、remove 顺序错、重试未回滚 |
| 偶发 / 概率性问题 | 加时间戳与序号，先证明是同一现象 | 竞态、时钟抖动、温度电压、固件状态残留 |

## 2. 取证手段清单

**Linux 侧**：`dmesg -w` 抓首次错误上下文；`/sys/kernel/debug` 下驱动统计；ftrace 看调度与中断延迟；`devmem` 直接读写寄存器；IOMMU fault 日志单独看。

**RTOS 侧**：预留的 ring buffer trace 点；串口高优先级输出；硬件计数器打点；必要时 JTAG 停核看现场。

**硬件侧**：逻辑分析仪抓 doorbell 与中断线；示波器看时钟复位时序；仿真器看固件指令流。
